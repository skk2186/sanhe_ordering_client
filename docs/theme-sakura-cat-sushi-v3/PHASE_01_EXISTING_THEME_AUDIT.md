## 当前正式主题怎样形成完整场景

当前 `ConveyorBeltDisplay.vue` 的 `SCENES` 和 `SettingDialog.vue` 只公开 `zhenxian`（蜡笔小新海滩）与 `xiaoxin`（海底贝壳）。两者的共同点不是简单换页面底色，而是各自有成套环境母图、载具、状态外壳和覆盖素材。

### `zhenxian`：海滩浅水

- 母背景为 `public/images/ui/b/background.png`；SCENES 将背景和进度条、船、贝壳托盘、转场拼贴列入预加载。
- `ScenicDishStage.vue` 为主题添加浅水漂流木板托盘，关闭默认潮流线；商品槽继续在同一条循环横向流里移动。`BeachBoatPass.vue` 将小船作为周期事件插入商品流，允许承载促销触发按钮；`StageSplashLayer.vue` 从船体可见位置推导吃水线并生成水花，而不是另造商品运动路线。
- `AmbientSceneEffects.vue` 提供泡沫扫过、海面闪光、鱼影等低频氛围事件；转场使用 `b/transition/` 角色拼贴与泡沫层。

### `xiaoxin`：海底/海面

- 母背景为 `public/images/ui/c/background.png`，与海滩主题共用相同的页面与业务骨架。
- 菜品延用水流舞台和贝壳托盘。`SeaTurtlePass.vue` 把龟身、龟壳、头、四肢、托盘与水花拆成透明图层，组件分别驱动摆动，并提供分层图失败后的合成图回退；水花/泡泡由 Canvas 与环境效果补充。
- 转场使用 `c/transition/ocean-animals.png` 精灵拼图；环境事件切为泡泡、鱼影和焦散。

两套背景均被当作场景母图，具体尺寸以本轮目录/代码没有直接解码核验为准；`themev2` 审计记录标注其为 3840×1080。后续 V3 应对新母图的实际像素尺寸单独验收，不沿用未验证假设。

## 组件外观怎样与场景统一

| 视觉区域 | 当前实现与主题化接口 | 后续可沿用的机制 |
| --- | --- | --- |
| 菜品舞台、餐盘与载具 | `ScenicDishStage.vue` 接收商品、分类、方向、速度、暂停与主题 key；商品仍是可聚焦 DOM，点击发出 `dish-click`。b 主题用漂流木板，c 主题用贝壳图；CSS 按主题切换形态。 | 保留商品数组、单条循环流、拖拽/滚轮/惯性、方向/速度/暂停、售罄与推荐状态和点击事件。以图像资产决定载具外形。 |
| 特殊事件 | 海滩船与海龟分别是独立 Vue 组件，复用舞台的周期事件槽位与促销事件；事件图像自身不承载业务商品数据。 | 可新建猫厨师/送餐车视觉组件，继续连接既有事件出口；角色动画不能接管商品流。 |

## themev2 值得借鉴的做法

- 先定义完整母背景、留白区、透视和资产边界，再动展示页；3840×1080 必须作为设计画布而非普通屏幕的放大版。
- 以真实视觉资产承担建筑、设备、复杂托盘、角色、灯笼和柜台等重要主体；把商品名/价格等可翻译可变化信息保留在 DOM。
- 保留同一商品流与特殊事件插入机制，让视觉载具改变“如何运送”的解释，不复制业务数据或运动状态。
- 拆件动画需要先设计锚点、遮挡次序与回退图；海龟拆件实例证明主体可以分层活动，也说明各层故障时需有整体回退。
- 用真实 3840/1920 浏览器画面、坐标测量和多类型商品验证比例与遮挡。themev2 的 R5R、R9R5 记录显示，仅凭设计稿会错判餐盘大小、信息区重叠与车身遮挡。
- 记录实际验证范围；没有做过的视觉/交互验收不能写成已通过。

## themev2 必须避开的路径

themev2 的 Phase 01 审计将其早期 `themev1` 月台实现作为失败样例：巨型 SVG 加大量 CSS 组合场景、轨道、托架和车轮，出现长宽比拉伸、细节不足、透视/光源各自为政、尺寸偏小、文字噪声和假纵深车道等问题。因此 V3 不得用 CSS 伪造整套日式店景，也不能先绘一堆符号再指望标题文案建立主题感。

themev2 后续报告还记录了实际餐盘/车身比例、顶部净空、前景遮挡反复修正；这说明静态图层合成需在 3840×1080 和 1920×1080 都实际校验，不能只按 clamp 计算后宣称验收。只引用“主题资料位于 themev2 分支”的事实：其 Phase 01 方案的验收结论不代表当前 V3 已验证。

## V3 必须复用的业务机制

1. `SCENES` 的唯一主题 key、背景/资产预加载、缓存合法性检查与主题切换生命周期；真正接入阶段再改，不在 Phase 01 动代码。
2. `ScenicDishStage.vue` 的真实商品/分类输入、循环横向流、方向/速度、拖拽/滚轮/惯性、暂停、商品点击/键盘入口、售罄/推荐状态及促销事件接口。
3. 父页面 `handleSushiClick` 根据屏幕左右半区决定加购侧；`useCart` 和既有左右四槽模型；`placeOrder` 的真实订单接口链路。
4. `TopPlateProgress` 的可访问进度语义和业务值；`CartPanel`、`CenterFunctionPanel` 的 props/emits 契约。
5. 设置中的语言、语音、方向/速度配置；招牌菜屏视频生命周期；主题切换 covering/covered/revealing 时序；环境动效暂停与 reduced-motion 约定。

## 可改视觉层与不可改业务边界

**可以改**：母背景和独立环境资产、猫厨师和托盘载具、餐盘按钮底图、回转台与服务台外壳、购物车/中控/进度外观、主题专属动画与场景转场、视觉布局层次和适配尺寸；可以增加纯视觉子组件或增加经过审慎设计的视觉 prop。

**本主题开发不得改写**：菜单/分类 API、商品字段与筛选逻辑、购物车数据模型及容量规则、商品点击至左右加购的路径、数量/删除/售罄规则、订单接口参数与提交流程、语音助手及推荐业务、订单历史、呼叫店员、方向/速度持久化语义、键盘加购与无障碍状态。视觉按钮必须继续发出原事件，主题变化不可改变点击结果。

## 本阶段结论

V3 最适合沿用现有的场景注册/预加载思想、单一商品流、三个主要主题外壳接口与可访问交互状态，同时以 3840×1080 的完整插画资产建立日式寿司屋。猫咪、弧形餐台、独立服务台、灯笼和窗景需先完成资产设计；代码只做定位、遮挡、点击热区与轻量状态动画。Theme V3 当前未加入 `SCENES` 或设置白名单。
