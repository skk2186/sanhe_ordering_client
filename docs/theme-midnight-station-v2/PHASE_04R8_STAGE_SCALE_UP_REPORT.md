## 为什么 R7R 的商品仍显小

R7R 的 3840 视口中，普通车身约 `320×107px`，菜图容器约 `200×134px`，按 `contain` 显示的 800×500 图片实际绘制约 `200×125px`。1920 视口下实际绘制约 `170×106px`。高细节的车站背景、铁轨和照明比商品更醒目；同屏商品数量偏多，也进一步削弱了单车的注意力。因此继续只放大菜图会让图片脱离车厢比例。

本轮将“约占画面三分之一”理解为运输单元成为明显视觉主体，而非让单张图片或单辆车机械地横跨屏幕三分之一。实现方式是增大普通车、商品图、槽位间距和特殊列车，并接受同屏可见车数减少；没有对整个舞台做 `transform` 放大。

| 3840×1080 | 菜图实际绘制 | 200×125px | 280×175px | 可见像素面积约 1.96 倍 |
| 3840×1080 | 车厢根容器 | 约 359×248px | 500×360px | 更完整地占据运输槽位 |

| 1920×1080 | 普通车身 | 286×95px | 400×133px | 宽、高约 +40% |

R8 铭牌在 3840 视口约 `211×104px`，菜名/价格实测计算字号为 `31px/34px`；1920 视口约 `176×87px`，字号为 `25px/26px`。字号沿用 R7R 可读级别，没有为了放大商品而缩小文字。

## 主舞台和铁轨关系

- 普通车槽位从 R7R 的 `359px/286px` 扩至 R8 的 `500px/440px`；横向间距从 `72–118px` 扩至 `84–118px`，给放大的车体和商品留出空间。
- 车厢高度由 `248px` 提至 `360px`（3840）/`320px`（1920）；车身宽度由 `320px` 提至 `480px`（3840）/`400px`（1920）。商品和车体仍在现有横向滚动流中，脚本、滚动机制和车轮运动数据未改。
- 共用轨道基线用 `clamp(390px, 45vh, 486px)` 定位，车厢的 rail drop 按基线减去当前车厢高度计算。3840 截图中的车轮与车身底部仍落在既有照片铁轨平面；1920 也没有压入分类栏或购物区。
- 铁轨、站台与夜景是同一张既有背景照片中的绘制内容，本轮没有编辑或重新缩放背景素材。车体/商品槽位尺度和轨道基线做了适配，但背景照片中铁轨自身的像素尺寸保持原样；这是当前资产合成方式的限制，截图中车辆、轮组与铁轨保持接触。

## 图片、滚动与页面检查

- 不同宽高比的商品图继续使用 `contain`，没有统一 `scale()` 裁切；示例 800×500 甜点图从 R7R 的 `200×125px` 提高到 `280×175px`（3840），1920 从 `170×106px` 提高到 `240×150px`。饮料、寿司/餐点图标、甜点、主食都出现在实际截图中，食物主体可见。
- 截图中的个别主食图片自身带深色背景，但商品主体可辨、图像正常加载，不是未加载的空黑圆；本轮没有过滤商品。
- 普通车点击、`dish-click`、左右方向、暂停、选中/推荐/售罄、键盘与可访问名称逻辑保持；共享滚动代码及车轮运动数据未变。特殊列车脚本保持不变。
- 分类栏、四槽购物区、搜索/记录/设置/呼叫按钮及其他主题未调整；3840 和 1920 全景均未见车轮/分类栏/底部购物区相互遮挡。
- Midnight 背景素材没有改动；`VirtualDiningAssistant`、`TopPlateProgress`、其他主题和订单状态逻辑保持冻结。测试继续验证这些边界。
